# 银枢 YinShu · 架构说明

本文说明系统分层、请求处理流程、模块职责和主要扩展点。

## 一、分层

```text
┌──────────────────────────────────────────────────────────────┐
│ 渠道层  frontend/index.html                                  │
│         对话、业务卡片、确认操作、执行轨迹                     │
└───────────────────────────┬──────────────────────────────────┘
                            │ POST /api/chat
┌───────────────────────────▼──────────────────────────────────┐
│ 编排层  backend/main.py                                      │
│         请求校验、状态机分派、响应装配、运维接口              │
├──────────────────────────────────────────────────────────────┤
│ 领域服务  backend/services/                                  │
│         确认、候选选择、风险上下文、视图与数字校验            │
├──────────────────────────────────────────────────────────────┤
│ 能力层  nlu / planner / presenter                            │
│         意图与槽位、模板计划、执行器、用户可读说明            │
├──────────────────────────────────────────────────────────────┤
│ 工具层  backend/tools/                                       │
│         工具注册、参数校验、幂等、HTTP 调用和结果归一化        │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP
┌───────────────────────────▼──────────────────────────────────┐
│ 基础层  Mock 银行核心（独立进程） + SQLite                    │
│         银行数据、会话、审计、幂等记录                        │
└──────────────────────────────────────────────────────────────┘

横切模块：security/（注入、策略、数字校验、审计、身份、脱敏）
         core/（配置、日志、指标、中间件、时钟、幂等、请求上下文）
```

业务工具调用统一经过 `backend/tools/gateway.py`，便于集中执行白名单、参数校验、幂等和错误映射。审计外部锚定使用独立的 HTTP 客户端，不属于业务工具网关。

## 二、请求流程

```text
用户输入
  └─ normalize + injection.scan
       命中强信号：直接拦截，不进入规划
  └─ nlu.parse
       生成 intent、slots 和候选实体
  └─ planner.build
       根据意图生成有界 DAG；运行时实体使用引用绑定
  └─ executor.run("preview")
       执行未标记为受控的步骤，收集账户、收款人、产品等事实
  └─ services.context + policy.decide
       构造风险上下文，执行硬规则和加权评分
  ├─ CONFIRM
  │    保存计划、预览结果和决策，返回确认卡
  │    用户确认后重新 preview、重算指纹、重新决策
  │    通过条件更新抢占执行权，再执行受控步骤
  ├─ AUTO
  │    直接执行受控步骤，使用幂等键提交
  ├─ HANDOFF
  │    终止自动执行，生成人工处理提示
  └─ DENY
       终止执行并记录拒绝原因
  └─ presenter + guard
       装配回复和卡片，对回复及部分卡片文本执行数字来源校验
  └─ audit.append
       追加哈希链记录
```

预览阶段并不是严格的只读阶段。工具是否受控由注册表元数据决定，未标记为受控的步骤可能在决策前执行。涉及资金或不可逆状态变更的工具应标记为受控，并通过 `registry.assert_invariants()` 在启动时检查配置。

## 三、模块职责

| 模块 | 职责 |
|---|---|
| `nlu/slots.py` | 中文金额、相对时间、收款人、人数、产品和商户关键词解析 |
| `nlu/intent.py` | 18 类意图的规则识别，确认、取消和否定句判断 |
| `planner/contracts.py` | `Step` / `Plan` 契约、步数限制和受控标记 |
| `planner/planner.py` | 意图到模板 DAG 的转换 |
| `planner/executor.py` | 两阶段执行、引用解析、事实集提取和失败补偿 |
| `planner/fingerprint.py` | 对计划与解析后的真实参数生成指纹 |
| `tools/registry.py` | 工具 schema、资金属性、可逆性、幂等要求和启动期不变量检查 |
| `tools/gateway.py` | 业务工具调用的统一出口，负责幂等、重试和结果归一化 |
| `security/injection.py` | 15 条注入规则、不可见字符和同形字检测 |
| `security/policy.py` | 配置驱动的硬规则和风险评分 |
| `security/guard.py` | 回复与部分卡片文本的数字来源校验 |
| `security/audit.py` | 追加哈希链、检查点、锚定和校验 |
| `security/identity.py` | Principal、HS256 JWT 和设备信息解析 |
| `security/pii.py` | 审计落库前脱敏和原文 HMAC 摘要 |
| `session/fsm.py` | 会话状态机与确认态 CAS |
| `session/store.py` | SQLite 会话持久化 |
| `services/confirm.py` | 待确认事务、确认时重新检查与执行 |
| `services/choose.py` | 候选卡与选择结果处理 |
| `services/context.py` | 风险上下文、账户解析和漂移分类 |
| `services/view.py` | JSON 化、通知卡、响应体装配 |
| `presenter.py` | 结构化结果到用户可读文本和卡片的转换 |
| `core/*` | 配置、日志、指标、中间件、时钟、幂等和请求上下文 |

## 四、确认与幂等

确认流程用于处理预览与执行之间的状态变化：

1. 预览结果和计划写入会话；
2. 用户确认时重新执行预览，读取当前余额、收款人和频率等状态；
3. 重算参数指纹，与确认前保存的指纹比较；
4. 重新运行策略引擎；
5. 使用 `UPDATE ... WHERE version = ?` 抢占执行权；
6. 执行受控步骤，使用确认事务 ID 参与幂等键生成。

指纹覆盖解析后的真实参数，而不只是计划模板。这样可以避免同一模板在确认时解析到不同收款人。

## 五、身份与数据隔离

身份优先级：

```text
Authorization: Bearer <JWT>
  → Principal(uid, device, ip, channel)
  → 工具网关透传 X-User-Id
  → Mock 银行按主体过滤账户、收款人、卡片、持仓、订阅和锁资金记录
```

约束：

- 请求体中的身份字段不被接受；
- 资源归属校验失败时返回错误，不回退到默认用户；
- 会话绑定所有者，跨主体操作被拒绝；
- 默认账期账户按主体解析，不使用固定账户 ID。

JWT 由本服务签发，适合演示和集成测试。生产环境应改为统一身份服务或网关注入身份。

## 六、数据存储

| 文件 | 内容 | 策略 |
|---|---|---|
| `data/bank.db` | 账户、卡、收款人、流水、理财、订阅、转账、锁资金 | SQLite WAL，可通过种子脚本重建 |
| `data/app.db` | 审计哈希链、锚点、幂等记录 | WAL，追加写入，支持增量和全量校验 |
| `data/session.db` | 会话和待确认事务 | WAL，状态变化时写入，TTL 默认 30 分钟 |

SQLite 适合单机演示和小规模部署。接入生产数据库时，应保持存储接口、审计追加语义和会话版本号约束。

## 七、扩展点

| 需求 | 需要修改 |
|---|---|
| 接入真实银行核心 | 工具注册表、网关鉴权、请求/响应映射、错误码、超时和幂等约定 |
| 接入模型生成话术 | `presenter` 的文本生成部分；规划和策略仍由现有模块执行 |
| 替换数据库 | `session/store.py`、`backend/mock_bank/db.py` 及其调用方 |
| 增加渠道 | 新增 adapter，映射身份、设备、幂等键和会话 |
| 调整权限阈值 | `config/policy.json` 及对应策略测试 |
| 新增业务动作 | 注册工具、添加计划模板、配置 `policy.json` 基础权重、补充测试 |

新增动作必须同时在工具注册表、策略配置和计划模板中完成，启动期不变量检查会拒绝缺失配置的工具。

## 八、设计取舍

- 规则 NLU 和模板计划的结果可复现，便于测试和审计；代价是长尾表达覆盖有限。
- 所有决策在服务端完成，前端不能提交风险档位或可信设备结论。
- 会话状态持久化，便于恢复待确认事务；代价是 HTTP 接口并非完全无状态。
- 关键操作采用两阶段处理，减少误执行；代价是确认流程比单次调用更复杂。
