# 银枢 YinShu · 架构说明

> 读这一篇能回答三个问题：分了几层、请求怎么流动、改哪里能换掉某一层。

## 一、分层

```
┌──────────────────────────────────────────────────────────────────────┐
│ 渠道层  frontend/index.html（手机壳 UI）· 未来：公众号 / 企微 / App    │
│         只做展示与输入，不含任何业务判断                               │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ POST /api/chat {session_id, text}
┌───────────────────────────────▼──────────────────────────────────────┐
│ 编排层  backend/main.py                                               │
│   输入隔离 → NLU → 规划 → 预览执行 → 权限决策 →（确认后）受控执行      │
│   → 幻觉校验 → 审计上链 → 卡片装配                                     │
├──────────────────────────────────────────────────────────────────────┤
│ 能力层  nlu（意图/槽位） · planner（契约/DAG/执行器） · presenter（话术）│
├──────────────────────────────────────────────────────────────────────┤
│ 工具网关 backend/tools/gateway.py —— **访问外界的唯一出口**            │
│   白名单 · 参数校验 · 幂等键 · 重试 · 结果收敛                         │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ HTTP（连接池）
┌───────────────────────────────▼──────────────────────────────────────┐
│ 基础层  Mock 核心系统（独立进程 8010）· SQLite（数据/会话/审计）        │
└──────────────────────────────────────────────────────────────────────┘

横切：security/（injection · policy · guard · audit）  core/（config · logging · metrics · middleware）
```

**为什么网关是唯一出口**：把"能碰钱的地方"收敛到一处，才能在这一处统一做白名单、校验、幂等与审计。
编排层直接 `requests.post` 一次，所有安全设计就漏一个口子。

## 二、一次请求的数据流

```
text
 └─ injection.scan()            命中 strong → 直接拦截（不规划）
 └─ nlu.parse()                 intent + slots（金额/时间/人/产品/商户/尾号）
 └─ planner.build()             模板 DAG，金额写成 $ref:slots.amount
 └─ executor.run("preview")     只跑只读步骤（查账户、搜收款人、筛产品）——此时一分钱没动
 └─ policy.decide(ctx)          硬规则 → 打分 → 注入降级 → AUTO/CONFIRM/HANDOFF/DENY
 ├─ CONFIRM: session.await_confirm(plan, out, decision) → 返回确认卡（含"为什么要你确认"）
 └─ AUTO   : executor.run("commit") → 真正划钱（幂等键 + 失败补偿）
 └─ presenter.build()           人话 + 卡片；数字只来自模板与事实集
 └─ guard.check()               回复里的每个数字都要在事实集里
 └─ audit.append()              sha256 哈希链（每条动作一行）
```

关键设计：**决策发生在执行之前**，且决策结果（含 plan 与 preview 结果）被持久化进会话，
所以"用户点确认"这一步不需要重新规划——也就没有"重新规划时被注入新指令"的窗口。

## 三、模块职责

| 模块 | 只有一件事 |
|---|---|
| `nlu/slots.py` | 中文金额（五百 / 两千五 / 一千二）、相对时间、人名、人数、产品/商户关键词 |
| `nlu/intent.py` | 18 类意图的规则级联；确认/取消词判定 |
| `planner/contracts.py` | `Step`/`Plan` 契约：工具必须在白名单内、步数上限、`is_gated` |
| `planner/planner.py` | 意图 → 模板 DAG（纯函数，无 IO） |
| `planner/executor.py` | 两阶段执行、`$ref` 解析、模糊收敛、失败补偿、事实集抽取 |
| `tools/registry.py` | 工具元数据：参数 schema、是否资金类、是否可逆、是否幂等 |
| `tools/gateway.py` | 唯一出网口：校验、幂等、重试、结果归一 |
| `security/injection.py` | 16 条规则 + 不可见字符/同形字检测，分级为 clean/suspicious/high |
| `security/policy.py` | 代码级权限引擎；每一分都有对应的人话理由 |
| `security/guard.py` | 事实集校验（防编数字） |
| `security/audit.py` | 哈希链、校验、按 trace 回放 |
| `session/fsm.py` + `store.py` | 状态机 + 落盘（重启不丢待确认事务） |
| `presenter.py` | 结构化结果 → 人话 + 卡片（含确认卡行装配）；所有数字走模板 |
| `core/*` | 配置、结构化日志、指标、中间件（限流/鉴权/体积/请求上下文）、时钟、幂等、请求上下文 |

### v1.1 新增的分层（领域服务）

`backend/main.py` 只留 HTTP 编排（路由、状态机分派、运维接口、错误处理、装配）；
领域逻辑下沉到 `backend/services/`，这一层**不允许 import fastapi**，
因此可以被评测脚本、其他渠道 adapter、将来的 gRPC 入口直接复用：

| 模块 | 只有一件事 |
|---|---|
| `services/view.py` | JSON 化、通知卡、卡片文本抽取、幻觉校验、工具输出注入扫描、统一响应体 |
| `services/context.py` | 风险上下文（世界状态 → `policy.Context`）、确认态快照、漂移分级 |
| `services/confirm.py` | 待确认事务落盘、确认卡装配、**确认时重新 preview + 重算指纹 + 重新决策 + CAS 抢占** |
| `services/choose.py` | 候选卡应答、选项解析、澄清态槽位补全 |
| `security/identity.py` | 主体（Principal）、HS256 JWT、设备信任判定 |
| `security/pii.py` | 审计落库前脱敏 + 原文 HMAC 摘要 |
| `planner/fingerprint.py` | 计划指纹（绑定解析后的真实参数） |
| `core/idempotency.py` | 服务端幂等表（抢占 / 回放 / 冲突） |
| `core/reqctx.py` | 请求级 ContextVar（主体 / trace / 幂等种子） |
| `core/clock.py` | 统一时钟（测试可冻结、演示可钉小时） |

### 版本化入口

`/api/*` 是唯一注册的路由；`/api/v1/*` 由 `VersionAlias` 中间件在进路由前改写成 `/api/*`。
**不要**再用 `include_router` 挂两遍——FastAPI 0.162 下 `include_in_schema=False`
不生效，会让 OpenAPI 每个接口重复一份并刷 Duplicate Operation ID 警告。

## 四、扩展点（换掉某一层，其他层不动）

| 需求 | 改哪里 | 不用改 |
|---|---|---|
| 接真实银行核心 | `registry.py` 的 `path/method` + `gateway.py` 的鉴权头 | 编排、规划、安全、前端 |
| 接大模型润色话术 | `presenter.build()` 的 `text_out` 一段 | 规划与决策（仍走模板与策略引擎）|
| 换数据库 | `mock_bank/db.py`、`session/store.py` 的实现类 | 业务代码（走 Store 协议）|
| 加渠道（微信/企微/App） | 新写一个 adapter 转发 `/api/chat` | 后端全部 |
| 调权限阈值 | `config/policy.json` | 任何代码 |
| 加新业务动作 | 在 `registry.py` 注册工具 + `planner.py` 加模板 | 安全层自动生效（`is_gated` 由元数据推导）|

## 五、为什么不用现成 Agent 框架

- 编排逻辑约 350 行，模板 DAG 是**确定性**的；引入框架换来的是调试成本与不确定行为。
- 安全插点需要精确控制（预览与执行分离、确认前不划钱），框架的执行语义未必匹配。
- 演示现场要求"断网也能跑、每次结果一致"，规则 + 模板比模型调用更稳。

这不是排斥模型：`config.py` 已留 `YINSHU_LLM_*`，定位是**只改话术、不改决策**——
模型说什么都不影响"办不办、办多少、要不要人工"。

## 六、数据与状态

| 文件 | 内容 | 一致性策略 |
|---|---|---|
| `data/bank.db` | 账户/卡/收款人/流水/理财/订阅/转账（仿真） | WAL + `synchronous=NORMAL`，可随时 `--reset` |
| `data/app.db` | 审计哈希链（只追加） | WAL；`/api/audit/verify` 全链校验 |
| `data/session.db` | 会话与待确认事务 | WAL；状态变更才写；TTL 30 分钟 |

三者都是 SQLite 单文件，演示与容器场景够用；生产建议换成行内已有的 DB/缓存，
接口契约（`Store` 协议、审计 append 语义）保持不变。
