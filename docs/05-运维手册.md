# 银枢 YinShu · 运维手册

> 面向部署/值班同学。所有命令都在本仓库根目录执行，Windows / Linux 通用（路径按需替换）。

## 一、三种运行形态

| 形态 | 命令 | 适用 |
|---|---|---|
| 演示 | `python start.py` | 现场演示、评审本机试跑（单进程、无限流、自动开浏览器）|
| 生产（裸机） | `python start.py --prod` | 服务器直跑，多 worker + JSON 日志 + 限流 |
| 容器 | `docker compose up -d --build` | 完整环境（后端 + Mock 核心系统 + 数据卷 + 健康检查）|

首次运行前：`pip install -r requirements.txt`（开发另需 `requirements-dev.txt`）。
数据默认在 `data/`，可用 `YINSHU_DATA_DIR` 指到挂载卷。

## 二、启动与停止

```bash
# 演示
python start.py                 # 自动造数 + 起 8010/8000 + 开浏览器
python start.py --reset         # 重建演示数据后启动（演示前必跑）

# 生产
YINSHU_ENV=prod YINSHU_WORKERS=4 YINSHU_API_KEYS=<k1,k2> python start.py --prod

# 容器
docker compose up -d --build
docker compose ps
docker compose logs -f app
docker compose down            # 停止（数据卷保留）
```

停止：裸机 `Ctrl+C`（start.py 会 terminate 子进程）；容器 `docker compose down`。

## 三、健康检查与监控

```bash
curl -s localhost:8000/healthz          # 存活：{"ok":true}
curl -s localhost:8000/readyz           # 就绪：核心系统通才 200，否则 503
curl -s localhost:8000/api/health       # 详情：bank / audit / policy / version / env
curl -s localhost:8000/metrics          # Prometheus 文本
curl -s localhost:8000/api/audit/verify # {"ok":true,"total":1282,"tail":"069e13a38ccb"}
```

建议告警项：

| 指标 | 建议阈值 |
|---|---|
| `/readyz` 连续失败 | ≥3 次 / 1 分钟 |
| `rate(yinshu_errors_total{code="INTERNAL_ERROR"}[5m])` | > 0 |
| `yinshu_http_request_seconds` P95 | > 1s |
| `yinshu_rate_limited_total` 突增 | 环比 3 倍（可能是攻击或阈值过低）|
| 审计链 `ok=false` | 立即 P0 |

## 四、日志

- 格式：`YINSHU_LOG_JSON=1` 出 JSON（生产默认），否则出便于人读的行。
- 一行一个事件，关键字段：`request_id`、`method`、`path`、`status`、`ms`、`ip`。
- 排查一条请求：先拿响应头 `x-request-id`，再 `grep` 日志；审计侧用 `trace_id` 调 `/api/audit/{trace_id}`。

```bash
docker compose logs app | grep '"request_id": "84afe3c6"'
```

- 日志不打印完整卡号/账号（统一 `mask()` 打码），也不打印用户原文全文。

## 五、演练：重启不丢"待确认的那一笔"

这是本项目的核心承诺，建议上线前手动跑一遍：

```bash
# 1) 制造一个待确认事务
python - <<'PY'
import httpx
c = httpx.Client(base_url="http://127.0.0.1:8000", trust_env=False)
r = c.post("/api/chat", json={"text": "给我妈转8000"}).json()
print(r["session_id"], r["debug"]["decision"]["tier"])   # AWAIT_CONFIRM / CONFIRM
open("sid.txt","w").write(r["session_id"])
PY

# 2) 杀掉后端（模拟发布/崩溃）
#    Windows: taskkill /PID <pid> /F    Linux: kill -9 <pid>
#    容器:    docker compose kill app

# 3) 重启后端
docker compose up -d app     # 或 python start.py --no-open

# 4) 用同一个 session_id 确认
python - <<'PY'
import httpx
sid = open("sid.txt").read().strip()
c = httpx.Client(base_url="http://127.0.0.1:8000", trust_env=False)
print(c.post("/api/chat", json={"session_id": sid, "text": "确认"}).json()["reply"])
PY
# 期望：打印「已向 … 转账 8000.00 元」，说明事务从库里被正确还原
```

确认有效期默认 5 分钟（`YINSHU_CONFIRM_TTL`）；过期会回「确认已超时作废，请重新发起」。

## 六、数据与备份

| 文件 | 内容 | 备份建议 |
|---|---|---|
| `data/bank.db` | 模拟银行（仅演示/联调） | 不备份，`--reset` 重建 |
| `data/app.db` | 审计哈希链 | **必须备份**，且只追加 |
| `data/session.db` | 会话与待确认事务 | 可选；丢失仅影响进行中的会话 |

```bash
# 在线备份（WAL 模式下安全）
sqlite3 data/app.db ".backup 'backup/app-$(date +%F).db'"
docker compose exec app python -c "import sqlite3;sqlite3.connect('/app/data/app.db').execute(\"VACUUM INTO '/app/data/backup.db'\")"
```

恢复审计库后务必 `curl /api/audit/verify`，断链会指出具体位置。

## 七、常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报 `bank=False app=True` | 8010 端口被占 / 核心系统没起来 | 先 `curl localhost:8010/v1/health`；或用 `YINSHU_BANK_PORT` 换端口 |
| `ERR_CONNECTION_REFUSED` | 后端未监听 | `curl /healthz`；看 `start.py` 输出是否提示依赖缺失 |
| 请求全部 502 | **系统代理接管了本机回环** | 代码已对本地调用 `trust_env=False`；若仍异常，`export NO_PROXY=127.0.0.1,localhost` |
| 响应突然变慢（>50ms） | 审计库没开 WAL（Windows fsync 慢） | 确认 `data/app.db` 为 WAL：`sqlite3 data/app.db "PRAGMA journal_mode"` 应返回 `wal` |
| 429 刷屏 | 限流阈值过低/共享出口 IP | 调 `YINSHU_RATE_LIMIT_RPM`；多 worker 下为进程内计数 |
| 401 全部接口 | 设了 `YINSHU_API_KEYS` 但客户端没带 | 加 `X-API-Key`；或临时清空该变量 |
| `确认已超时作废` | 超过 5 分钟 | 重新发起；或调大 `YINSHU_CONFIRM_TTL` |
| 演示数据被"玩坏"了 | 转账/取消订阅改变了状态 | `python -m backend.mock_bank.seed --reset` 或 `python demo.py --reset` |
| pytest 报 `PermissionError: pytest-of-...` | 本机 `%TEMP%` 受限 | 已在 `pyproject.toml` 固定 `--basetemp=.tmp/pytest`，确认 `.tmp/` 可写 |

## 八、容量与性能参考（本机实测，单进程）

| 场景 | 耗时 |
|---|---|
| 只读（账单/订阅） | 4–6 ms |
| 转账预览（2~3 次下游调用） | 8–15 ms |
| 审计写入 | 走 WAL，不阻塞读 |
| 会话落盘 | 仅状态变化时写（只读往返不写） |

优化记录：开启 WAL 前单请求约 80ms（每次审计 fsync），开启后降到 4~5ms；网关改用连接池后再降一档。

## 九、发布与回滚

1. `git tag v1.0.0 && git push --tags`；CI 跑测试 + 13 场剧本 + 评测 + 镜像构建。
2. 生产用镜像 `yinshu:1.0.0`，`docker compose up -d`（镜像不可变，回滚即换 tag）。
3. 回滚：`docker compose down && YINSHU_TAG=0.9.0 docker compose up -d`。
4. 数据兼容：审计库只追加；会话表结构变更需带迁移脚本（当前版本无破坏性变更）。
