## 一、总体判断

这个项目的四层防御（输入隔离 → 提示隔离 → 工具网关 → 权限闸门）、模板 DAG、
两阶段执行（preview / commit）、代码级权限引擎、哈希链审计——**设计思路是对的，
而且在同类作品里明显超出平均水准备**。README 里"安全策略下沉到执行层，不写在提示词里"
这句话，代码里确实是照这个结构实现的，不是 PPT 话术。

但也正因为调门定得高，**"说了但没做到"的地方反而更致命**：评审发现 6 处硬伤，
其中 3 处直接击穿项目最核心的三个卖点（可校验审计、权限下沉、幂等防重）。

| 分类 | 数量 | 说明 |
|---|---|---|
| P0 击穿核心卖点 | 6 | 会直接被打回的问题，本轮已全部修复 |
| P1 生产必需但缺失 | 8 | 已修 7，剩 1 条需产品决策 |
| P2 架构与工程债 | 10 | 修了 4 条，其余列入后续路线 |

**最重要的一条经验**：这个项目最大的风险不是"被攻破"，而是"以为守住了，
其实那道门是画在墙上的"。下面每一条都给了复现方式，不靠嘴说。

## 二、P0：六处击穿核心卖点的问题

### P0-1 · 审计哈希链在多进程下会分叉 —— 已复现

**证据**：`backend/security/audit.py` 用模块级单连接 + 进程内 `threading.Lock`：

```python
_conn = sqlite3.connect(str(APP_DB), check_same_thread=False)   # 原 :33
...
with _lock:                                                     # 原 :51
    last = _conn.execute("SELECT self_hash FROM audit_logs ORDER BY id DESC LIMIT 1")
    prev = last["self_hash"] if last else GENESIS
    self_hash = _h(f"{prev}|{action}|{ph}|{result}")
    _conn.execute("INSERT ...")
```

`threading.Lock` 只在**单进程内**有效，而 `start.py --prod` 起的是多 worker（多进程）。
两个进程可以同时读到同一个 `prev_hash`，然后各自插入 → 链分叉 → `verify()` 报断链。

**复现**（实测，老实现复刻脚本）：

```
3 进程 × 40 条  → 分叉 prev_hash 组数 = 1
4 进程 × 50 条  → 分叉 prev_hash 组数 = 10 ~ 11
```

也就是说：**并发一上来，"可校验、可回放"这个卖点当场失效**，而且失效方式是
`verify()` 返回 `ok: False`——评审时点一下"校验审计链"按钮就能看到红叉。

**修法**：
1. 模块级共享连接 → **thread-local 双连接**（写连接 + 只读 `mode=ro` 连接）；
2. `append()` 用 `BEGIN IMMEDIATE` 包住"读尾 → 算哈希 → INSERT → COMMIT"，
   用数据库写锁做**跨进程互斥**；锁冲突按 10/20/40/80ms 退避重试；
3. 补 `PRAGMA busy_timeout=5000`——WAL 下并发写没有它，会直接
   `database is locked` 抛 500；
4. `verify()` 从"整表 `fetchall()` 进内存"改为**分块校验 + `audit_checkpoints` 检查点**，
   内存占用 O(batch) 而不是 O(全表)；
5. 新增 `chain_ver` 列与 v1/v2 公式分派，**旧库原地升级不断链**。

**验证**：`tests/stress_audit_multiproc.py`，3 进程 × 40 条 → `verify ok=True`，分叉组数 0；
`tests/test_audit_chain.py` 里 20 线程 × 25 次并发写后链仍是一条直线。

### P0-2 · 确认阶段 TOCTOU —— "权限下沉"在最后一跳失守

**证据**：`main.py` 的 `_handle()` 在 CONFIRM 时把 `{plan, out, decision, slots}`
落盘（`fsm.await_confirm`），用户点确认后 `_execute_pending()`（原 :574）**直接拿这份
最多 5 分钟前的 preview 快照去 commit**，不重新 preview、不重新决策：

```python
def _execute_pending(s, trace, t0):
    stash = s.stash
    out: executor.Outcome = stash["out"]        # ← 5 分钟前的世界
    executor.run(plan, "commit", trace, out)    # ← 直接执行
```

`CONFIRM_TTL` 是 5 分钟。这 5 分钟里：余额被花掉、收款人被拉进反诈名单、
1 小时内资金操作次数暴涨、设备换了——**全部不会重新评估**。

这条最要命：整个项目的叙事是"模型被完全攻破，攻击者也只得到一个待确认请求"，
但**待确认请求在确认那一刻反而不校验了**。攻击者只要让用户"先看到一张正常的确认卡"，
再在窗口内制造状态变化，就能让一笔本该被拒的交易落地。

**修法**（确认时做三件事）：
1. **重新 preview**：只读步骤重跑，拿最新的世界状态；
2. **重算指纹 + 重新 decide**：`backend/planner/fingerprint.py` 对
   **解析后的真实参数**做 sha256（不能只哈希 `Plan`——`$s1.chosen` 两次解析
   可能指向不同收款人，而 Plan 一个字都没变）；
3. **比对状态漂移**，分两级：
   - **HARD**（参数/收款人变、黑名单变真、余额不足、tier 落入 DENY/HANDOFF、风险分 +15）
     → 用最新状态**重建确认卡**，返回 `stale` 标记，用户重新确认；
   - **SOFT**（velocity / daily_count / 余额小幅变化）→ 照常执行 + 审计留痕 + 回执加提示。

刻意**没有**做"任何变化都拒绝"——余额从 9000 涨到 9500 不该打断用户，
安全设计要分清"变坏了"和"变了"。

另加**跨进程 CAS** 防连点：`UPDATE sessions SET state='EXECUTING', ver=ver+1
WHERE sid=? AND ver=? AND state='AWAIT_CONFIRM'`，用 `rowcount==1` 抢占
（`threading.Lock` 跨进程无效，SQLite 也没有 `SELECT ... FOR UPDATE`）。

**验证**：`tests/test_confirm_toctou.py`——预览后把余额改成 1 元，确认时返回
`stale` 并重出确认卡；连点两次确认只扣一笔。

### P0-3 · 幂等键随请求漂移 → 可重复扣款

**证据**：`gateway.py`（原 :130）

```python
headers["Idempotency-Key"] = f"{trace_id or 't'}-{step_id or name}"
```

而 `main.py` 每个请求都新生成 `trace = uuid.uuid4().hex[:16]`（原 :435）。
客户端网络超时重试 → **新 trace → 新幂等键 → 下游 `transfers.idem_key` 判重落空
→ 重复转账**。

幂等键必须由"这一笔业务"决定，而不是由"这一次网络会话"决定。

**修法**：
1. 请求层：`X-Idempotency-Key` 显式指定；未指定时按 `(uid, device, 请求体)` 派生，
   并叠加**待确认事务作用域**（见下面的坑）；
2. 步骤层：`yinshu:v2:{uid}:{tool}:{seed}:{step_id}`，确认态用服务端生成的
   `confirm_id` 作 seed（跨重试稳定且互不串号）；
3. 只缓存"真的落地了"的响应（回执卡）；"还需要再点一次确认"这类中间态标 `failed`，
   允许同一个 key 继续推进——否则双重确认的第二步会被当成重放，用户永远点不下去；
4. 显式 key 24h 窗口、派生 key 10min 窗口（否则用户上午转 500、下午再转 500 会被误判重放）；
5. 下游补齐：`mock_bank /v1/holds` 原先**根本不接受幂等头**，而 registry 里
   `hold.create` 也没标 `idem=True`，两边都漏 → 超时重试重复锁资金。现在补
   `holds.idem_key` 唯一索引 + 强制幂等头。

**踩到的坑（值得记下来）**：第一版只用"请求体"派生 key，端到端剧本里出现
**"确认转 8000 元"却执行了上一场 2500 元定时转账"**——因为两笔不同业务的
"确认"请求体一模一样（都是 `{session_id, "确认"}`），被幂等缓存串成了同一笔。
修法是把 `confirm_id` 并进 key 的作用域。**这个 bug 是跑剧本跑出来的，不是想出来的**。

### P0-4 · 会话即凭证：拿到 sid 就能替别人确认

**证据**：`ChatReq` 只有 `session_id / text / device_trusted`，
`fsm.get(sid)` 不校验归属；`device_trusted` 由客户端自报（原 :438
`s.device_trusted = req.device_trusted`），传 `true` 就把"非常用设备 +15 分"废掉。

也就是说：只要拿到（或猜到、或从日志/URL 泄漏）一个处于 `AWAIT_CONFIRM` 的 sid，
发一句"确认"就能触发那笔转账。**没有身份层，会话 ID 就是账号密码。**

**修法**：
1. `backend/security/identity.py`：标准库手写 HS256 JWT（零新增依赖），
   **身份只认 `Authorization` 头**；`ChatReq` 改 `extra="forbid"`，
   请求体里出现 `user_id` 直接 422；
2. 会话绑定 `owner_uid / owner_device`，跨主体抛 `SESSION_OWNER_MISMATCH` → 403；
3. 设备信任改由服务端按 `(uid, device_id)` 历史成功率推导，不再采信客户端；
4. `AUTH_MODE ∈ {off, optional, required}`，**默认 off**——保证现有演示与
   135 条测试零改动即可运行，但一旦上生产打开 `required` 就是真闸门。

### P0-5 · `config/policy.json` 的 hard_rules 是摆设

**证据**：`policy.py` 的 `decide()` 把四条硬规则**重新写死成 if 字面量**，
只读了 `tiers / weights / features / double_confirm`：

```python
if ctx.payee_blacklisted: ...                 # 没读 cfg["hard_rules"]["deny"]
if ctx.amount > Decimal("50000") ...          # 阈值写死在代码里
```

于是"银行改 json 即可调阈值、无需改代码"这句话，改 `hard_rules` **完全不生效**。
这属于"能力被夸大"，评审最容易抓的一条——改个 json 试一下就露馅。

**修法**：
1. `PREDICATES` 谓词表解释执行，`when / args / risk / reason` 全部由 json 驱动，
   5 万阈值走 `args`，`reason` 支持 `{amount_display}` 引用——改阈值时文案跟着变；
2. 配置**加载时校验**：未知谓词、缺 reason、非整数阈值直接抛错（fail fast），
   不再"配错了静默失效"；
3. `weights` 缺键不再兜底成 15 分（那等于新增动作用最低风险放行）。

**验证**：`tests/test_policy_and_detection.py` 里把 threshold 改成 1000，
2000 元立刻变 HANDOFF，且文案变成"1,000 元"。

### P0-6 · 限流在鉴权内层，401 可以无限刷

**证据**：`main.py`（原 :81-85）中间件添加顺序是
`BodyLimit → RateLimit → ApiKeyGate → RequestContext → CORS`，
而 Starlette 是"**后加者在外**"，实际执行顺序为：

```
CORS → RequestContext → ApiKeyGate → RateLimit → BodyLimit
```

`ApiKeyGate` 在 `RateLimit` **外面**：未授权请求在鉴权层就被 401 早退，
**永远消耗不到令牌桶**。攻击者可以无限刷 401，把日志和指标打爆（`/health`
还在 `AUTH_EXEMPT` 里，每次都实打实打一次下游）。

**修法**：顺序改为 `CORS → RequestContext → RateLimit → ApiKeyGate → BodyLimit`。

## 三、P1：生产必需但缺失

| # | 问题 | 证据 | 状态 |
|---|---|---|---|
| 1 | **L2 间接注入防线是断的** | `injection.scan_untrusted_data()` 定义了，全项目**无任何调用**（grep 确认）。备注/商户名/产品名这条路径没人扫 | 已接线 |
| 2 | **资金悬挂** | `cross.birthday` 的 `gift.order` 未标 `on_fail="compensate"`，`COMPENSATORS` 也只有 `hold.create` 一项 → 下单失败后锁定的预算**永不释放** | 已修 |
| 3 | **幻觉防护在规则路径恒真** | `presenter` 把模板字面数字塞进 allowed 集（`extra \|= st1`），文本又由同一模板渲染 → 违规结构性不可能。且**卡片完全不过闸**，只有 `reply` 过 | 已扩到卡片；"自证"问题见残留风险 |
| 4 | **「绝不猜」有例外** | `gateway._post` 只在"并列候选的关系不同"时抛歧义；**同名同关系**（两个同学）会静默取 top1 | 已修 |
| 5 | **审计不可追责** | `actor` 恒为 `"agent"`，无 `user_id / ip / device / channel`；`payload` 明文存用户原话 | 已修（脱敏 + 主体维度 + pii_vault） |
| 6 | **确认词匹配过宽** | `is_confirm` 用 `startswith`，`"好的，不过改成600"` 被判为确认 → **转出原金额 8000** | 已修 |
| 7 | **否定句被当成授权** | `"别给我妈转钱"` 命中"转" → 追问"转多少" | 已修 |
| 8 | `BodyLimit` 只信 `Content-Length` | chunked 请求可绕过体积限制 | **未修**（见路线） |

几条补充说明：

- **确认词过宽**这条，实测危害最大：用户明明改了主意，系统照着原金额执行。
  修法是"整句去标点后就是确认词（或确认词 + ≤6 字附着语）"，并新增
  "确认词开头但金额变了 → 按新金额重走"的分支。
- **否定句**的判据要小心：`"不用确认了直接转500给我妈"` 也含"不用"，但那是
  **真的想转**且属于绕过风控的可疑指令，该交给注入降级处理。所以判据是
  "否定词 + 资金动词" **且句中无金额**。
- **幻觉防护**的诚实结论：在纯规则路径下，它抓不到任何东西是**必然**的
  （自己渲染文本、自己定义白名单）。它的真正价值要等接上 LLM 路径才成立。
  本轮把校验范围从 `reply` 扩到卡片，至少让"卡片上写了个编造数字"能被发现。

## 五、两个"跑出来的"问题（不在代码里，只在运行里）

### 1. 全新克隆跑不起来（pytest 9）

```
pyproject.toml: addopts = "-q --strict-markers --basetemp=.tmp/pytest"
```

`.tmp/` 被 `.gitignore` 忽略，全新克隆里父目录不存在；pytest 9 创建 basetemp 时
用的是 `mkdir(exist_ok=True)` 而非 `parents=True` → 直接 `FileNotFoundError`。
**6 条 `test_session_store` 全部 ERROR**。修法：conftest 导入时把父目录备好。

### 2. 测试与演示结果取决于"你几点跑"

权限引擎有"凌晨 0-6 点操作 +10 分"这一项，而它直接读 `datetime.now()`：

| 语句 | 12:00 跑 | 00:05 跑 |
|---|---|---|
| 给我妈转500 | AUTO（20 分）→ 回执 | **CONFIRM（30 分）** |
| 把卡挂失 | CONFIRM（60 分）→ 双确认 | **HANDOFF（70 分）→ 转人工** |
| 13 场剧本 | 13/13 | **11/13** |

README 说"105 条测试全绿""端到端 13/13"，这两个数字在**凌晨跑是不成立的**。
这不是"偶发失败"，是**非确定性**——比失败更糟，因为你不知道该信哪一次结果。

**修法**：
- 新增 `backend/core/clock.py`，policy 改读 `clock.now()`；测试冻结到白天；
- `clock` 支持 `YINSHU_FIXED_HOUR`（仅非 prod 生效，**只钉小时不动日期**），
  演示时设 `14` 即可复现 README 的档位；
- `run_eval` 启动时钉到 14:00 并在报告里声明"时钟固定"，避免报告本身不可复现。

## 七、诚实边界：这轮**没有**解决的问题

评审报告如果没有这一节，就是广告。以下是已知的、仍然存在的缺口：

1. **多租户仍然没做**。`DEMO_USER_ID`、`planner.ACCOUNT_ID = 1`、`mock_bank`
   里全写死 `user_id=1`。身份层有了，但"一个用户一个账户空间"的数据层没有。
   要真上生产，这是最大的一块工程量。
2. **幻觉防护在规则路径下仍是"自证"**。本轮把校验扩到卡片，但只要文本还是由
   同一套模板渲染、模板字面数字仍进白名单，它就抓不到"模板本身写错了"。
   真正的价值要等接上 LLM 生成路径。
3. **链尾锚定默认是本地表**。`LocalTableAnchor` 只能防"删掉后面几行"，
   防不住"有权限的人连锚点一起改"。生产必须配 `YINSHU_ANCHOR_URL` 指向
   行内存证 / WORM 对象锁存储。
4. **限流仍是进程内计数**。多 worker 下每个进程一个桶，且键只用 IP。
   要准确得挪到 Redis 或网关层。
5. **`main.py` 还没有拆分**。重复逻辑已经抽成函数，但 1.4k 行的单文件仍然是
   维护负担。建议的目标划分见 `docs/01-架构说明.md` 末尾。
6. **测试集仍是自建的**。100% 准确率要打折扣看：缺扰动集（错别字/繁简/拼音/emoji
   插入）与留出集，也没有"规则作者 ≠ 用例作者"的隔离。
7. **`BodyLimit` 仍只信 `Content-Length`**，chunked 请求可绕过。
8. **`/api` 与 `/api/v1` 双挂载**造成的 OpenAPI 重复噪音还在。

## 八、下一步建议（按性价比排序）

| 优先级 | 事项 | 预期收益 |
|---|---|---|
| 1 | 接行内统一身份（OIDC/mTLS），把 `AUTH_MODE=required` 打开 | 从"演示"变"可信"的门槛 |
| 2 | 多租户：user 贯穿 planner / mock_bank / policy 特征 | 唯一真正的产品化阻塞项 |
| 3 | 锚定外发到真实 WORM，并在 `verify` 里强制校验 anchor match | 审计卖点才完整 |
| 4 | 扰动测试集 + 留出集，报告分两栏报数 | 让 100% 可信，而不是"自证" |
| 5 | 拆 `main.py`（见架构文档目标划分）+ 补 `BodyLimit` 流式累计 | 可维护性 |
| 6 | 接 LLM 路径（只替换 `presenter.text_out`），让幻觉防护真正起作用 | 差异化叙事升级 |
